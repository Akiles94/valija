# Spec: delivery — CLI, MCP server, composition root

`src/delivery/` sits at the top of the dependency graph: it wires `vault` + `context` + `shared` into runnable entry points. It is not a bounded context.

## container.ts

`buildContainer(options?: { vaultRoot?: string })` (GUI advance) is the single composition root: constructs the infra adapters (`Argon2VaultCrypto`, `OsKeychain`, `FileVaultStore`, `SqliteVaultSessions`, `FileExportReader`, the `parserRegistry`) and injects them into every use case — including `ImportConversations`, wired over an `ImportItems` write path. The CLI keeps calling `buildContainer()`; the desktop app passes `vaultRoot` resolved from its own preferences (D-R(a)), and rebuilds the container after a successful relocation. `resolveVaultPaths(options?.vaultRoot)` — an explicit root still beats `VALIJA_HOME`, which still beats `~/.valija`, unchanged. Both entry points share one container. M3 adds `FileDeviceIdentity` (over `resolveStatePaths()`), `FileVaultFolder`, and a `SessionGuard` built from `parseAutoLockTtl(process.env.VALIJA_AUTOLOCK_MINUTES)` — threaded into `SqliteVaultSessions`, `CreateVault` (to start the idle clock at init), `UnlockVault`, `LockVault`, and `VaultStatus`. `Container` also exposes the already-constructed `folder: VaultFolder` (GUI advance), `mover: VaultMover` (GUI advance, D-R(c) — the desktop's relocation pre-flight reads `c.mover.inspect(...)` directly, the same instance `RelocateVault` uses, rather than constructing a second `FileVaultMover`), `relocateVault: RelocateVault` (GUI advance, D-R(c)), and `checkVaultUpgrade: CheckVaultUpgrade` (GUI advance, D-J(b)) — `doctor.ts` reads `c.folder` rather than constructing a second `FileVaultFolder`. **PROJECT-DETECT** adds one shared `FileWorkspaceProbe` and four fields — `resolveProject: ResolveProject`, `linkWorkspace: LinkWorkspace`, `unlinkWorkspace: UnlinkWorkspace`, `listProjectBindings: ListProjectBindings` — plus `envProject?: string`, `process.env.VALIJA_PROJECT` read once at build time (the same posture as `VALIJA_AUTOLOCK_MINUTES`; absent when unset). The container does not interpret it: delivery passes it to `ResolveProject`, which parses it.

## context-pack-markdown.ts

`renderContextPackMarkdown(pack)` turns an assembled `ContextPack` into markdown: the `# Context pack:` header, one `##` per section, and `### type · date · #tags` per item. **Formatting lives here, not in the domain** — the domain orders sections, delivery names and renders them. Shared by `cli/` (`export`) and `mcp/` (`get_context`).

## context-pack-export.ts (GUI advance)

`exportProjectMarkdown(c, project)` and `exportProjectJson(c, project)` — the two compositions `cli/content-commands.ts`'s `exportCommand` used to build privately, lifted out so the desktop app's pack view/export calls the *same* functions rather than a second copy. `exportProjectMarkdown` is `GetContextPack({ budgetTokens: Number.POSITIVE_INFINITY })` + `renderContextPackMarkdown`, unbudgeted — this is what makes "byte-identical to `valija export`" a structural property, checked against the golden fixture in `context-pack-export.test.ts`, rather than a test that can drift as the two call sites evolve independently.

## diagnostics.ts (GUI advance)

`runDiagnostics(c): Promise<DiagnosticCheck[]>` — the check *computation* `cli/doctor.ts` used to own privately, lifted out (D-T) so the desktop app's Diagnostics screen reads the same verdicts rather than re-deriving "is the vault healthy" a second time. Same `DiagnosticCheck` shape (`{ name, ok, detail, fatal? }`), same check names (`node`, `sqlcipher`, `keychain`, `vault`, `journal`, `sync`, `lineage`, `auto-lock`, one per `CLIENTS` entry) and the same order as before the extraction — `doctor.ts`'s own stdout stays byte-identical, checked against a fixed check list in `cli/doctor.test.ts` rather than against the environment's real keychain, which is not injectable and observably flaky in a sandboxed CI runner. The four checks derived from `VaultStatus.execute()` (`vault`, `journal`, `lineage`, `auto-lock`) also carry an optional `errorCode` alongside `detail` when that read fails — `doctorCommand` never reads it, so stdout is unaffected, but the desktop app's Diagnostics screen localizes from it instead of rendering `detail`'s raw `DomainError.message` on screen (D-V(d); the Copy report stays the one place that raw text may still appear).

## cli/ — `valija <command>`

| Command | Behavior |
|---|---|
| `init` | Prompt passphrase twice (hidden on a TTY); print recovery kit once; vault starts unlocked. |
| `unlock [--recovery-key <hex>]` | Session control via the keychain. Always calls `UnlockVault` with `upgradeConfirmed: true` (GUI advance, D-J(b)) — the CLI keeps migrating a behind-schema vault silently, byte-identical to before that gate existed. On success, if the lineage classifies as a **fork** (M3, D-B), the vault still unlocks (for inspection) and a `VAULT_FORK_DETECTED` notice prints alongside the vault folder path — no exit-1, so the user isn't stranded from `doctor`, the tool that helps resolve it. |
| `lock` | Drops the key; on a real unlock→lock transition reports the generation and the last writer (as `this device`/`another device` **with a short device-id prefix**, so a three-device fork is tellable). The "single file (vault.db) — safe to switch" reassurance prints **only when no sidecars remain** (refined §6.5); if stray `-wal`/`-shm`/`-journal` files are present it prints a "NOT safely at rest" warning instead, never both. |
| `status` | Session control via the keychain, plus (M3) journal mode + single-file state, lineage generation/last-writer (short device-id prefix) when unlocked, and the auto-lock TTL/idle state. |
| `projects` / `show [p] [--type]` / `search <q> [-p]` | Read views. `show --type imported` lists imported items. `show` prints each item's **full id** in its header (`— type · date  id <id>  📌  [tags]  [archived]`); `show --archived` includes archived items, marked `[archived]` (CURATION). **PROJECT-DETECT:** with `[p]` omitted, `show` picks the project with `chooseProject` over `process.cwd()` (remedy: `Pass a project name, or link this folder: valija link <project>.`) and prints no detection note; `search` without `-p` stays vault-wide (D-F). |
| `pin` / `unpin` / `archive` / `unarchive <id>` | (CURATION) Curate one item, addressed by full id or a unique ≥6-char prefix (`ITEM_ID_AMBIGUOUS` lists the candidates). Prints `Pinned decision <id> in project "<p>".` — `archive` adds `Undo: valija unarchive <id>` — or `Already pinned — nothing changed.` on a no-op. Prints ids, types and project names only, never content. |
| `edit <id> [--content-file <file\|->] [--tags a,b] [--type t] [--allow-secrets]` | (CURATION) Edit in place. Content comes from a file or stdin (`-`); there is no inline `--content` (shell history) and no `$EDITOR` (a plaintext temp file). `--tags` replaces the list; `--tags ""` clears it. No flags → `NOTHING_TO_EDIT`. **SECRET-WARN:** new content that looks like a secret fails with `error [POSSIBLE_SECRET]: <kinds and lines>. Nothing was saved. Remove it, or re-run with --allow-secrets to save it anyway.` (exit 1, no prompt); `--allow-secrets` saves it anyway. A tags/type-only edit never rescans content. |
| `export [p] [--json] [-o file]` | Context pack to stdout/file — the escape hatch for non-MCP tools. md = `GetContextPack` with an infinite budget, rendered; json = `ShowProject` serialized as `{ project, items }`. With `[p]` omitted the project is detected exactly as for `show`; the output bytes are those of the explicit export, and `-o`'s `Exported <p> (…)` line names the resolved project. |
| `which [--dir]` | (PROJECT-DETECT) `ResolveProject` over `--dir` (default cwd). Prints `valija  (linked repository github.com/oscar/valija)`, `… (linked folder ~/code/x)`, `… (VALIJA_PROJECT)`, or `No project detected here.` plus, when an existing project matches the repository's name, `Hint: a project named "<p>" matches this repository's name. Link it with: valija link <p>`. Nothing found exits 0; `VAULT_LOCKED`, `INVALID_WORKSPACE_PATH` (not raised when `VALIJA_PROJECT` decides) and a bad `VALIJA_PROJECT` exit 1. |
| `link <p> [--dir] [--by repository\|folder]` | (PROJECT-DETECT) `LinkWorkspace`. Prints `Linked repository <target> → project "<p>".` (plus a line saying any clone on any synced device now resolves to it) or `Linked folder <~path> → project "<p>".`; a re-link prints `Already linked: … Nothing changed.` and writes nothing. `--by` is validated by commander `.choices()` (P-13). |
| `unlink [id] [--dir] [--by]` | (PROJECT-DETECT) `UnlinkWorkspace` by id, or by the binding `--dir` (default cwd) resolves through, optionally narrowed by `--by`. An id together with `--dir`/`--by` → `error: give a binding id or --dir/--by, not both.`, exit 1, before any use case runs. Prints `Unlinked <kind> <target> from project "<p>".` |
| `links [p]` | (PROJECT-DETECT) `ListProjectBindings`: `ID  PROJECT  KIND  TARGET` (P-7 — the id is what `unlink` takes), columns padded to their widest cell; or `No folders or repositories are linked yet. Link one with: valija link <project>`. |
| `import <file> -p <p> [--from] [--list] [--pick] [--query] [--since] [--all] [--dry-run]` | Import chatbot history. **No selection flag → lists conversations and writes nothing** (the safe default); `-p` required for a real import or `--dry-run`. Auto-detects chatgpt/claude unless `--from` is given (`generic` requires it). Prints `Imported N item(s) from M conversation(s) into "<p>" (skipped S, failed F)`. **SECRET-WARN `[--allow-secrets]`:** all-or-nothing. A refused real run prints `error [POSSIBLE_SECRET]: Import refused: N chunk(s) …`, one `  #n "title" part p — kinds (lines)` line per blocking chunk (`(title hidden)` when the title is flagged; `#n` is the `--pick` number), and the remedy, to stderr, and exits 1 with nothing written. `--dry-run` prints the counts line, then `A real import would be REFUSED: …` and the same lines to stdout, exit 0. See [importers.md](importers.md). |
| `install <claude-code\|claude-desktop\|cursor>` | Merge the MCP entry into the client config, backing up first; refuses to touch non-object/invalid JSON; prints manual fallback. `installIntoClient(client, vaultPath?)` (GUI advance, D-R(a)'s companion step) — the CLI's own call site never passes `vaultPath`, so the entry it writes has no `env` block and is byte-identical to before; the desktop app always passes one, from both the ordinary connect flow and the relocation wizard's re-pointing step, one shared writer serving both. |
| `mcp` | Run the stdio server (used by tools, not humans). |
| `doctor` | Check node ≥22, sqlcipher load, keychain r/w, vault state, client configs, and (M3) journal/single-file state, cloud-folder recognition with a lock-before-switch reminder, a loud warning on a vendor conflicted-copy file **or a leftover `*.pre-NNN.bak` from a failed upgrade**, lineage generation/last-writer (short device-id prefix), and auto-lock TTL/idle state. The vault status is computed **once** and shared across the four M3 checks (each `execute()` opens the db), not recomputed per check. All four M3 checks are advisory — never fatal, never exit non-zero. **(GUI advance)** the check computation itself now lives in `../diagnostics.ts`'s `runDiagnostics` — `doctorCommand` only prints its rows (`✓`/`✗`, name padded to 16, detail) and exits 1 on a fatal failure. |

Errors print `error [CODE]: message` and exit 1 — `fail(error, remedy?)` appends a surface-specific remedy when one applies (SECRET-WARN: the `--allow-secrets` hints) (the fork notice on `unlock` is the one deliberate exception — see above).

**Env vars:** `VALIJA_PROJECT` (PROJECT-DETECT) — names the project to use whenever one is omitted, ahead of any linked folder or repository; read once by the container, treated as explicit (it may name a project that does not exist yet). An invalid value fails with `INVALID_PROJECT_NAME` naming the variable. **(M3)** `VALIJA_AUTOLOCK_MINUTES` — idle auto-lock TTL in minutes; unset/empty defaults to 15, `0`/`off` disables it. `VALIJA_STATE_HOME` — device-local state root (device id, per-vault last-seen, last-activity); defaults to `~/.valija-state`, independent of `VALIJA_HOME` so it never lands in a synced folder. There is no `init --cloud <path>` flag — placing a vault in a synced folder needs no special-casing, just point `VALIJA_HOME` at it (see [../docs/sync.md](../docs/sync.md)).

Binding commands live in `cli/binding-commands.ts` (thin: call, `fail()` on error, print — never item content). Folder targets are shown with `~` for the home folder (`displayTarget`); remotes are already credential-free.

## project-detection.ts (PROJECT-DETECT)

Shared by the CLI and the MCP server, like `context-pack-export.ts`. `chooseProject(c, explicit, directories, remedy)` → `{ project, detectedBy? }`: an explicit name returns at once — no session, no probe, no env read — so an explicit call is byte-identical to before; otherwise `ResolveProject` with `c.envProject`, and `none` → `PROJECT_NOT_DETECTED` (`No project was given and none is linked to this workspace.` + an optional name-match hint + `remedy`), `ambiguous` → `PROJECT_AMBIGUOUS` (slugs only + `remedy`). Messages never carry a path or a remote. `detectionLabel(kind)` → `linked folder` / `linked repository` / `VALIJA_PROJECT`, the only detection words a response shows. `displayTarget(view, home?)` → a folder with `~` for home, a repository as-is (CLI and desktop display only).

## mcp/server.ts — server name `valija`, stdio

Five tools — `save_context`, `save_handoff` (forces `handoff` type), `get_context`, `search_context`, `list_projects` — plus prompts `/save-context` and `/load-context`. Every input is zod-validated at the boundary. `save_context`'s type enum is `ITEM_TYPES` (the five saveable types) — `imported` is **not** offered, so a model can never create an imported item; import stays CLI-only. On a locked vault, tools return `isError` with the uniform message: *Vault is locked. Ask the user to run "valija unlock" in a terminal.* The MCP client's declared name is captured into each item's `source`. **CURATION:** `save_context` takes an optional `supersedes` (max 64 chars, an exact id — no prefix) and appends `Archived superseded item <id>.` to its response; `search_context` lines read `- [project] (type, date, id <id>) content`. Still five tools, still two prompts; no `pinned` argument anywhere; `get_context`, `list_projects` and the prompts are unchanged. **SECRET-WARN:** `save_context` and `save_handoff` map a `POSSIBLE_SECRET` error through `refusal(error)`, which appends `SECRET_REMEDY_FOR_MODELS` ("Remove it or replace it with a placeholder such as <API_KEY>, then call the tool again. If it is not a secret, describe it instead of quoting it.") before the usual ` [CODE]` suffix; every other error and every other tool is untouched. The remedy never mentions an override, and the server has no `allowSecrets` anywhere (D-N). Both save descriptions gain one sentence: content that looks like a credential is refused with POSSIBLE_SECRET and nothing is saved. No input schema changed.

**PROJECT-DETECT:** `project` is optional on `save_context`, `save_handoff` and `get_context` (`required` is `["content"]`, `["content"]`, `[]`); `search_context` is unchanged — omitted still means vault-wide. An omitted `project` goes through `chooseProject` with the directories from `mcp/workspace-directories.ts` and the remedy *Call list_projects, ask the user which project they mean, then pass it as `project`.*; a given one returns at once, without asking the client for roots, so the explicit text is byte-identical. Save replies append ` (detected: <label>)` (`detectionLabel`) — never a path or a remote; `get_context` output is exactly `renderContextPackMarkdown` (no detection line); `list_projects` appends ` (this workspace)` to the detected project's line (binding or `VALIJA_PROJECT`, P-14), and a failed detection leaves it unmarked. `/load-context` takes an optional `project`: without one, its first line tells the model to call `get_context` without a project and, on `PROJECT_NOT_DETECTED`, call `list_projects` and ask; `/save-context` without a project says to call `save_context` without `project`. The handlers read only `project` and `detectedBy` from the resolution, never `locations` or `binding`. Still five tools and two prompts.

## mcp/workspace-directories.ts (PROJECT-DETECT)

`workspaceDirectories(server, env)` (D-C): if the client declared `roots` (`getClientCapabilities()`, checked first so `listRoots` never throws), `roots/list` with a 2 s timeout, keeping `file:` URIs that name existing directories; when roots are undeclared, empty, failing or slow, the server's cwd — unless `isNonWorkspaceDirectory(cwd, env)`: the filesystem root, home or an ancestor of it, inside node's install folder or `~/.npm`, `/Applications`, `/System`, `/Library` on macOS, `%ProgramFiles%`, `%ProgramFiles(x86)%`, `%LOCALAPPDATA%\Programs` on Windows (P-3). `WorkspaceEnvironment` (cwd, home, platform, execDir, variables) is injected so tests never touch the real home. Roots and cwd come from the client process, never the model; nothing is cached (D-S). Imports only `node:fs`, `node:os`, `node:path`, `node:url` (guarded by `detection-no-spawn.test.ts`).

What each client actually provides is **assumed, not yet observed** — `advances/PROJECT-DETECT/spike.md` §2: Claude Code is assumed to declare one root (the project) and start the server in it; Claude Desktop is assumed to declare no roots and start it in `/` (macOS) or an app folder (Windows), so detection there falls through to `PROJECT_NOT_DETECTED` unless `VALIJA_PROJECT` is set; Cursor is assumed to declare roots (its open folders) in recent versions, with a cwd that is not the workspace.

The tool descriptions are the product's real prompt engineering — see [../docs/SPEC.md](../docs/SPEC.md) §7.
